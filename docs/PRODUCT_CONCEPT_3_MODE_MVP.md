# REA Studio — 최종 제품 계약과 3모드 MVP 구현 기준
작성: 2026-10-18 KST. 사용자 확정 제품 콘셉트. 현행 구현 성공 주장 아님.

## 제품 한 문장
**허가된 웹사이트 하나를 분석해 독립 실행형 앱 초안을 만들고, 같은 분석 결과로 (1) 원본형 (2) 디자인 변경형 (3) 사용자 데이터/스키마 적용형 결과물을 생성하는 로컬 제작 도구.**

## 최종 사용자 경험
URL 입력 → 사용자 권한/범위 확인 → 원본 수집 및 구조/기능 증거화 → 공유 SiteBlueprint 생성 → 3가지 모드 중 선택 → 독립 실행 가능한 결과 생성 → 나란히 미리보기 → 화면/동작 비교 → 한정된 자동 보정 → 코드/증거/검증 리포트 내보내기.

### MODE 1: Faithful Reconstruction — 원본형
- 입력: 허가된 정확한 URL, 명시적으로 승인된 조회/상호작용 범위.
- 출력: 원본과 최대한 유사한 **독립 구현** HTML/CSS/JS 앱, 비교 결과.
- 목표: 장기적으로 고객이 명시한 페이지/뷰포트/사용자 흐름에서 시각·행동 측정 기준 99%에 접근. '모든 사이트 99%'는 보증 불가. 원본 소스코드/비공개 API/DB/비밀번호/결제/인증을 자동 복원한다고 주장하지 않는다.
- 모르는 기능은 UNVERIFIED 또는 별도 동의한 MOCK으로 표시.

### MODE 2: Design Remix — 디자인 변형형
- 입력: 동일한 SiteBlueprint, 테마 프리셋 또는 디자인 변경 설명.
- 출력: 변경된 색/타이포/레이아웃/컴포넌트 스타일을 적용한 독립 앱, 변경 내역 및 전후 비교.
- 원본의 구현된 기능 인터페이스를 재사용하되 미검증 동작을 실제 원본 동작처럼 표시하지 않는다.
- 사용자가 준 재디자인 지시는 안전한 CSS/디자인 토큰 형태로 적용하며 임의 스크립트를 무검증 삽입하지 않는다.

### MODE 3: Schema-driven Adaptation — 내 데이터 기반 재구성형
- 입력: 동일한 SiteBlueprint + 사용자가 설명한 목적/정보구조 + JSON 데이터/스키마(초기에는 로컬 파일/텍스트).
- 출력: 레이아웃 패턴을 참고하되 필드·차트·표·카드·필터가 사용자 데이터에 맞게 재편성된 독립 앱.
- 필드명→UI 컴포넌트 매핑, 샘플 행 렌더링, 명시적 mock/실제 데이터 표기, 데이터 미존재 오류를 제공한다.
- 비밀키, 원본 고객 개인 데이터, 외부 DB 연결정보를 기본 수집/전송하지 않는다. 실제 DB 연결과 서버 API는 추후 별도 승인 및 계약.

## 모든 모드가 공유하는 내부 섹터
| 섹터 | 입력 | 출력 | 오늘의 목표 |
| --- | --- | --- | --- |
| A. Target + Permissions | URL, 사용자 권한 확인 | 허가된 분석 요청 | 기존 정확한 URL allowlist 유지 |
| B. Observation | 승인된 페이지/기존 저장 증거 | screenshot, DOM/geometry, observation-status | 기존 static-visual 경로 재사용; 새로운 외부 사이트 자동 방문 없음 |
| C. Shared Blueprint | B의 확실한 정보 | viewport, regions, types, components, evidence refs, unknowns | 기존 P4 geometry 변환. 빈 정보는 unknown 처리 |
| D. Three Renderers | C + mode-specific options | 3개 별도 독립 HTML 빌드 | 세 경로가 최소 수준으로 모두 파일을 반환 |
| E. Preview + Compare | 원본 screenshot + 생성물 | 나란히 보이는 두 이미지/상태 라벨 | 원본 대비 미리보기, 데이터 없는 경우 명확히 미검증 |
| F. Export | 생성된 HTML + manifest | 실행 가능한 결과물 + 생성 설명 | 모드별 HTML 다운로드 + 정보출처/제약 |
| G. Validation | A~F | 실패 항목과 테스트 로그 | 세 모드에서 최소한 한 번 end-to-end 검증 |

## 오늘의 '구동되는 MVP' 계약 (우선순위)
**목표는 기존 보안 기능 정밀화가 아니라 한 사이트의 저장된 분석 결과를 대상으로 세 모드가 끝까지 돌아가는 하나의 작업 화면이다.**
1. 기존 Studio에 별도 **3 MODE BUILDER** 작업 화면 또는 패널 추가. URL/기존 분석 선택, 3모드 선택, Mode 2 스타일 프리셋/설명, Mode 3 로컬 JSON/스키마/요구사항을 입력할 수 있게 한다.
2. 입력 → `SiteBlueprint` 정규화 → **세 변형을 모두 빌드**하는 연결을 우선한다. 초기는 현행 `static-visual`의 저장된 합법적 증거와 기존 `generateP4Reconstruction` 또는 격리된 fixture를 재사용한다.
3. MODE 1은 스크린샷 전시가 아니라 독립 HTML/CSS 결과를 반환한다. 실제 외부 JS/API/DB의 재현률을 허위 주장하지 않는다.
4. MODE 2는 MODE 1 결과에서 최소 두 디자인 토큰(예: 색/서체) 변경이 화면에서 확인되도록 한다.
5. MODE 3은 사용자가 준 JSON 스키마와 예시 데이터를 **실제 화면의 표/카드/수치에 반영**하고 최소 한 가지 로컬 인터랙션(예: 필터/검색 또는 정렬)을 작동시킨다. 외부 DB 접속은 하지 않는다.
6. 모든 결과는 로컬 preview와 별도 HTML 다운로드로 확인 가능하고 모드 변경 시 기존 출력이 섞이지 않는다.
7. 최소 한 개의 **통제된 사용자 소유/합성 테스트 대상**으로 3개 모드를 순서대로 실행하여, 캡처/저장→세 결과 렌더→다운로드 재검증까지 통과한다. 이 검증은 타사 실사이트 재현을 증명하지 않는다.
8. 시간 부족 시 우선순위: **세 모드 화면·연결·작동 증거** > 시각적 충실도 향상 > 부가 API/ZIP/보안 리포트 추가. 실패 기능은 '지원 안 됨'으로 명시하고 정상처럼 보여주지 않는다.

## MVP 명시적 비범위
- 사이트 무관 범용 시각 99% 재현, 모든 메뉴/페이지 자동 탐색, 인증된 세션, 로그인/결제/서버/DB 자동 복원, 타사 사이트 접근/권한 변경.
- 사용자의 사전 승인 없이 새로운 외부 origin에 GET/POST/클릭을 실행하는 작업.
- 제3자 저작물을 무단 배포하기 위한 픽셀 복제. 고객 소유 또는 허가된 사이트로 검증한다.
- 제품 라이선스/판매용 제작자 코드 품질과 SLA 달성 주장.

## 인터페이스와 검증 경계
- `SiteBlueprint`는 현재 관찰된 사실(evidence)과 추정(inferred), 미확인(unknown)을 구분하는 구조화 JSON. 기존 저장된 P4 geometry/P5 메트릭을 우선 활용하되 임의로 기능을 채우지 않는다.
- `BuildRequest`: `{ run_id, mode: "faithful"|"remix"|"schema", theme?, requirements?, user_schema?, sample_data? }`.
- `BuildArtifact`: `{ mode, status, preview_url, download_url, source_scope, evidence_status, limitations, artifact_sha256 }`. 이 스키마는 *계약 초안*이며 아직 API/파일로 구현되었다는 의미가 아니다.
- GET은 항상 저장 결과 조회/다운로드만 수행. 새로운 분석·빌드는 사용자 명시 POST로 분리하고, 기존 Host/Origin/Allowlist·데이터 크기 제한 유지.
- 실제 데이터는 사용자가 로컬에서 명시한 범위만 사용. 샘플/모의 데이터를 보이면 MOCK/SAMPLE 레이블 필수.

## 완료 판정 — '제품 전체 골격 먼저'
- UI: 세 모드가 첫 화면에서 각각 입력값, 현재 단계, 미리보기, 결과 다운로드를 표시.
- 엔드투엔드: 1개의 고정/허가된 저장 분석으로 **세 모드 모두 실제 HTML 파일 생성** 확인, 가짜 버튼만 있는 UI 불인정.
- 차이 확인: MODE 2는 MODE 1과 시각적으로 다르고, MODE 3은 사용자 데이터 변경 시 결과가 실제로 달라짐.
- 안전성: 모드 전환·재조회는 새 외부 요청을 만들지 않으며 기존 승인/보안 경계 유지.
- 테스트: 단위 테스트 외 **실제 Studio HTTP 경로/브라우저 기능 검증**, 최신 GitHub Actions Linux/Windows 별도 확인.
- 정밀화는 이 MVP가 구동되고 상호 연결이 증명된 다음에 시작.

## 구현 진행 방식
제품 콘셉트 → 최종 화면과 7개 섹터 골격 → 3개 렌더러를 낮은 충실도로 먼저 연결 → 한 사이트 전체 흐름 검증 → 부문별 시각/기능 정확도 향상 → 각 변경 후 교차 통합 검증. 추가 기능의 로컬 완벽성보다 3가지 고객 가치의 전체 작동을 먼저 검증한다.
